# AGENTS.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Remora is a type-safe Python DSL for Wireshark/tshark capture analysis. It drives tshark subprocesses directly (no pyshark): field access is statically typed via `.pyi` stubs, display filters are built from expression trees instead of strings, and predicates are pushed down to tshark where possible. Work is organized by milestone epics (#40 M1 kernel, #41 M2 codegen, #42 M3 polish, #43 M4 DuckDB workspace); each epic issue defines the execution path and dependency graph.

## Commands

Everything runs through uv (Python ≥3.10; CI matrix is 3.10–3.14):

```bash
uv sync                                        # install deps
uv run pytest                                  # full test suite
uv run pytest tests/test_planner.py -v         # one file
uv run pytest tests/test_fields.py::TestScalarInstanceAccess::test_static_types -v  # one test
uv run pytest -m "not integration"             # skip tests needing a real tshark binary
uv run mypy --strict src tests                 # typecheck (tests included — this is the CI gate)
uv run ruff check .                            # lint
uv run ruff format --check .                   # format check (also formats code fences in docs/*.md)
```

The CI gate is all four: `ruff check`, `ruff format --check`, `mypy --strict src tests`, `pytest`. Run the full gate before committing.

Static typing assertions are part of the test suite: `assert_type(...)` calls in `tests/` are no-ops at runtime and are verified when mypy checks the test files. Beware that a preceding `assert x == value` can narrow a type and break a later `assert_type` — put `assert_type` before runtime asserts.

## Workflow

- One PR per issue. Branch `feat/issue-<n>-<slug>` (or `feat/<n>-<slug>`), PR body includes `Closes #<n>`. PRs are squash-merged, so merged local branches need `git branch -D`.
- **Process artifacts are issue comments, not repository files.** Design docs, specs, implementation plans, and progress notes go into the issue as `gh issue comment <n>` — they belong to the issue's history, not to the shipped tree. Only durable documentation (`docs/*.md`, ADRs, `AGENTS.md`) is committed. `docs/superpowers/` is gitignored scratch space — anything under it is local to one checkout and is not part of the tree.

## Architecture

Data flow for a query: **Expr IR → planner → tshark argv → reader → RawPacket → protocol view / predicate**.

- `src/remora/expr.py` — immutable expression IR, deliberately a leaf module (imports nothing from remora). Comparisons on fields build `Expr` trees via `FieldExprOps`; `__bool__` raises so `and`/`or`/chained comparisons fail loudly (use `&`/`|`/`~`, parenthesize comparisons). There is **no `Ne` node**: `!=` builds `Not(Comparison(EQ, ...))`, making Wireshark's multi-value `!=` pitfall unrepresentable. `FieldRef`s are intentionally unhashable (`__eq__` returns an `Expr`); dedup by `.name`.
- `src/remora/values.py` — the single source of truth mapping tshark ftypes (`"FT_IPv4"` …) to Python types and parse functions. Parse errors raise `ValueError` (loud beats silent); unknown ftypes fall back to `str`. `coerce_literal` normalizes user literals at compile time for both backends.
- `src/remora/fields.py` — the contract hub. `RawPacket` is the minimal packet protocol: `get_raw(name) -> tuple[str, ...]` with `()` meaning absent. `Field`/`MultiField` are dual-mode descriptors: class access (`IP.src`) returns a `FieldRef[T]` for building expressions; instance access (`pkt[IP].src`) returns `T | None` (scalar) or `tuple[T, ...]` (multi). Multiplicity is encoded in the descriptor *class* because `@overload` can only express the return type per class.
- `src/remora/compile/` — three backends lowering `Expr`: `dfilter.py` renders Wireshark display-filter strings (raises `UnsupportedExprError` for what it can't push; `!=` always renders `!(f == v)`), `predicate.py` compiles Python predicates over `RawPacket` (the end of the fallback chain — mirrors Wireshark semantics exactly, including any-occurrence matching on multi-value fields). `sql.py` is the third target (#29), lowering the same IR to a DuckDB predicate string plus bound parameters for the workspace query path: it learns column name, SQL type and multiplicity from the field ref alone (`naming.column_name`, `types.get_column_type`/`column_sql_type`), so nothing here re-derives a frozen policy, and it stays import-pure — plain strings and plain Python values, never duckdb. Multi-value fields keep any-occurrence semantics (`list_contains(col, ?)` for `==`, `len(list_filter(col, x -> x <op> ?)) > 0` for the ordered operators), the DSL's `!=` renders `NOT (...)` and never SQL `<>` on a list column, and a `Membership` range becomes `col BETWEEN ? AND ?` (multi: `len(list_filter(col, x -> x BETWEEN ? AND ?)) > 0`) — which is the subnet predicate, since #26 stores addresses as integers precisely so a prefix test is a zone-map-friendly range. `FT_IPv6` is the one ftype whose placeholder is `CAST(? AS UHUGEINT)`, because its encoder emits decimal text. IEEE-754 NaN **is** harmonized to Python's semantics, unlike NULL, because DuckDB gives `DOUBLE` a total order where NaN equals itself and sorts greatest: a NaN literal compiles to the constant `FALSE` binding no parameter (so `x != nan` is `NOT (FALSE)` and selects every row, and a NaN membership element or `ValueRange` endpoint — checked before the inverted-range test, which every-comparison-is-false would otherwise skip — is `FALSE` too), and `>`/`>=` on a float column carry a `NOT isnan(...)` guard (scalar `("col" > ? AND NOT isnan("col"))`, multi `x -> x > ? AND NOT isnan(x)`) so a stored NaN is excluded the way Python excludes it, while `<`/`<=`/`BETWEEN`/`=` are deliberately unguarded because NaN sorting greatest already makes them false and `inf` needs nothing at all. `Matches` is compiled since #36 — `regexp_matches(col, ?, 'i')`, wrapped in the portable-text guard below and, on a multi column, inside the any-occurrence `list_filter` — so `UnsupportedSqlExprError` now covers an unknown `Expr` node, a `matches` *pattern* `remora.compile.re2` rejects (lookarounds; a bounded repeat above 1000, counting the product of the factors along a nesting path, where `{m,}` contributes `m` and only `*`/`+` contribute nothing; and any non-ASCII pattern character — the RE2-only restriction, applied at SQL compile time rather than at `Expr` construction so the pcap path keeps the constructs PCRE2 and Python `re` run identically), and `contains` on a BLOB column — while malformed literals stay `ValueError`/`TypeError` exactly as in the sibling backends. NULL behavior **is** harmonized since #36, where #29 had stated the divergence and left it: a NULL-able leaf is wrapped as `coalesce(<leaf>, FALSE)` when — and only when — a `Not` will invert it, so `f != v` on an absent scalar selects the row exactly as Wireshark and the predicate backend do. **At the leaf**, because coalescing a whole subtree gets nested negation wrong (`NOT (NOT (x))` over a NULL leaf becomes TRUE where Python's `not not False` is False); **only under a `Not`**, because `coalesce` blocks DuckDB's scan-level filter pushdown and a positive leaf has no divergence to fix (a NULL reaching the `WHERE` clause is filtered out, which is what the other two backends do), so the hot equality and subnet-`BETWEEN` scans #26 stores integer addresses for keep the plan they had. `IS NOT NULL` (scalar) / `len(coalesce(col, [])) > 0` (multi, NULL-safe on back-filled columns) presence tests and the NaN `FALSE` constant are untouched, being two-valued already, and a multi column back-filled with `NULL` by a later `add_field_column` falls under the same rule. `matches` additionally carries a **portable-text guard**: the compiled predicate raises DuckDB `error()` naming the column on any value where `strlen(v) <> length(v) OR contains(v, chr(10))`, because RE2 matches runes where PCRE2 and Python `re` match bytes, folds case by Unicode, and anchors `$` at end-of-text only — so non-ASCII or newline-bearing text is exactly where the three engines disagree, and a loud refusal beats a quiet row-set fork. That guard is only sound paired with `re2.py`'s ASCII-only *pattern* rule, since Unicode folding reaches ASCII from outside it (U+212A folds onto `k`) and no value-side test can see a pure-ASCII value matched by a non-ASCII pattern. Two residuals, stated rather than implied: the guard is a property of the column's data rather than of the answer, so a query can fail on a row another conjunct would have excluded, and whether that row is examined at all can depend on zone-map skipping from other pushed-down filters. `tests/test_sql_duckdb.py` runs the shared semantics table (#7) — the absent-field truth table included — against a DuckDB seeded through the real `column_spec` codecs, and `docs/semantics.md` is the durable statement of both that truth table and the regex support matrix; the two describe the same machinery, so a change to one belongs in the other.
- `src/remora/planner.py` — two-level pushdown, pure decision, never spawns tshark. Pushable conjuncts become a `-Y` display filter; statically known field sets enable `-T fields` projection; opaque lambdas force `-T ek` whole-packet fallback. Failed-to-push `Expr`s become residual Python predicates.
- `src/remora/reader/` — `process.py` owns tshark subprocess lifecycle only (stderr drained by a daemon thread to avoid pipe deadlock; `close()` terminates/kills/reaps so no orphans). `fields_reader.py` parses `-T fields` output using literal `0x1f`/`0x1e` separator bytes embedded in argv (tshark has no hex-escape separator syntax). `ek_reader.py` parses `-T ek` NDJSON; ek key mapping is `layers["ip"]["ip_ip_src"]` (layer + `_` + dots→underscores).
- `src/remora/proto/` — protocol classes. `_meta.py` defines the **frozen compact-table format**: classes set only `_proto_` and `_table_: ClassVar[FieldTable]` mapping attr name → `(tshark_name, ftype, multi 0/1)`; descriptors are materialized lazily on first access (`ProtocolMeta.__getattr__` for class access, `ProtocolBase.__getattr__` for instance access) so a 10k-field module imports for free. Protocol modules are generated artifacts (#19): `codegen.toml` lists the core set and the curated multi-value fields; regenerate with `uv run python -m remora.codegen write` under the pinned tshark (in practice inside docker: `ubuntu:24.04` + `ppa:wireshark-dev/stable`, since the pin tracks CI's PPA — run it natively on the host's own architecture and never under emulation, because regeneration is architecture-neutral since #97: the canonicalized `-G fields` dump is the same text on amd64 and arm64 under one pinned tshark (a native arm64 run reproduces the committed `dump-sha256`, which CI's amd64 `codegen-drift` job keeps green from the other side), and the fingerprint's `env:` line hashes only the `(name, version, type)` columns of each `tshark -G plugins` record, dropping the fourth path column that embeds the multiarch triplet (`x86_64-linux-gnu` vs `aarch64-linux-gnu`) and used to confine reproduction to CI's amd64. The accepted cost is that a per-arch behavioral difference in a same-version plugin no longer flips `env:` — anything it changes about dissection still moves `dump-sha256`, which is the first line of defense; `.github/workflows/codegen-arch-verify.yml` is what puts both architectures' digests side by side: its two matrix legs each run `.github/scripts/codegen_arch_probe.py` natively on a GitHub-managed runner (`ubuntu-latest` and `ubuntu-24.04-arm`), refusing any tshark that is not the `codegen.toml` pin, and a separate `compare` job — which runs no probe of its own — downloads both reports and fails unless the version, dump digest and `env:` agree; it triggers on `workflow_dispatch` and automatically on pull requests touching `fingerprint.py`, the probe script, `codegen.toml` or the workflow itself — so a scheme or pin change re-proves the claim on both architectures before merging, while every other PR leaves it idle). `codegen.toml` also assigns extras-only protocols (`[extras.wireless|industrial|telecom]`) to the separate `remora-<extra>` distributions under `packages/` — each ships only leaf `remora/proto/<name>.py`/`.pyi` modules that graft into core's `remora.proto` at install time (`pkgutil.extend_path` merges editable/mixed installs); `remora.proto.__getattr__` imports installed extras lazily and raises an `ImportError` naming the extra (`pip install 'remora[wireless]'`) for missing ones; the generated `_extras.py` module→extra map stays in core next to `_meta.py`/`__init__.py`, and `write`/`check` cover every destination (`--packages-dir`); `remora[all]` means everything — the union of every other extra, protocol or not, which since #25 includes `workspace`'s duckdb (`tests/test_packaging.py` derives the union rather than listing it, and the CI `wheels` job therefore resolves `remora[all]` with `--find-links dist` instead of `--no-index`, since duckdb comes from PyPI) — all dists share core's version with exact pins, and the CI `wheels` job spot-checks built-wheel contents, the core-only `ImportError`, `remora[all]` resolution, and stub resolution. Each generated `.py` has a sibling `.pyi` stub that shadows it for type checkers, declaring `Field[T]`/`MultiField[T]` per attribute; `_meta.py` and `__init__.py` are the only hand-written files, ruff ignores E501 under `proto/` and the formatter skips the tree so committed bytes stay emitter-exact.
- `src/remora/codegen/` — the M2 generator's front and back halves. `parse.py` turns a `tshark -G fields` dump (`P`/`F` records) into frozen model dataclasses (`Protocol`, `FieldDef`, `FieldDictionary`); malformed, unknown, and duplicate lines become collected `ParseWarning`s (first occurrence wins) rather than silent drops. `mangle.py` is the frozen field-abbrev → attribute-name policy the emitter (#14) must follow; it is **not injective** (dots and hyphens both become `_`), so emitters must detect per-protocol duplicate mangled names. `tests/data/g_fields_sample.txt` is a checked-in subset of a real 4.6.7 dump (regenerate with `tests/data/make_g_fields_sample.py`); tests assert exact record counts against it. `emit.py` is the back half: `emit_protocol(protocol, fields, multi)` renders one protocol's paired `.py` (compact `_table_`, import-pure) and `.pyi` (one `Field[T]`/`MultiField[T]` attr per field) sources, byte-deterministic in input field order (reproducible bytes therefore require the canonicalized dump order from `fingerprint.py`, #68); multiplicity has no `-G fields` signal so the multi-abbrev set is caller-supplied, mangled-name collisions resolve first-wins — except that a data field displaces an earlier `FT_NONE` expert/structural marker (presence-only, no extractable value) for the shared attr name — and every collision path records an `EmitWarning`, and `mangle_protocol` (lowercase, non-alnum→`_`, digit→`p_` prefix, keyword→trailing `_`) names the module, upper-cased for the class. The contributor-facing procedures for all of this — Docker regeneration recipe, drift-check triage table, `psdsl gen` worked example — live in `docs/codegen.md`; the two describe the same machinery, so a change to one belongs in the other.
- `src/remora/workspace/` — the M4 DuckDB workspace. It owns the storage layout and catalog (#25) and, since #28, the `Workspace` class that owns *all* connection, lock and compaction policy: every other module here takes a caller-supplied connection and opens none of its own — the invariant is **connection ownership**, not abstinence from I/O in general, and `workspace.py` is the only module that opens a DuckDB connection. Most of the rest is layout, naming or codec logic that touches nothing but the connection it is handed, and exactly three modules do non-DB file or process I/O: `cachekey.py` reads the **capture**, never the workspace file, because a fingerprint is by definition a function of the capture's bytes, `export.py` stats the destination and its own temp file (it has to compare the destination against the database file, and it renames the finished export into place), and `materialize.py` runs tshark — `detect_tshark_version` spawns `tshark --version` outright, and a materialization drives the dissecting subprocess through its injectable `TsharkRunner` seam — while delegating that same capture read to `cachekey.py` for the fingerprint. None of the three opens a DuckDB connection or holds any of the lock, so connection ownership still belongs entirely to `Workspace`. Packet data lives in `main` (`pkts`, `streams`, `annotations`), the catalog in a dedicated `meta` schema (`meta.info` key/value including `schema_version`, `meta.fields`, `meta.cache_keys`), so `meta.fields` is a literal table reference and user SQL over `pkts` never trips on catalog names. `pkts` is created with only the row-key skeleton (`frame_number`, `frame_time`) — projected field columns are grafted on later by `add_field_column` — and deliberately has **no `PRIMARY KEY`**: DuckDB backs one with an ART index that taxes exactly the bulk append path #31 must keep cheap, so `frame_number` is the row key by convention (unique, ascending in capture order) rather than by constraint; the small catalog tables do keep their keys, because they take single-row writes and the constraint is the point. `annotations` (#30) and `streams` (#33) both started as documented placeholders — columns now, semantics there — and both now have their semantics; `annotations` cost no layout change at all, while `streams` gained four endpoint columns and a `UNIQUE (protocol, stream_id)` key in #33 plus the `annotations.protocol` column that key forced, and that **is** a layout change, so `SCHEMA_VERSION` went to 2 — "nobody had populated the placeholder" is not an exemption, because `create_schema` is `IF NOT EXISTS`-only and cannot add a column to an existing file, so a v1 workspace that still opened would carry a `streams` table missing the columns this layout's SQL names and fail as a raw DuckDB binder error inside `build_streams()` instead of as a refusal at open (a reviewer reproduced exactly that). `iter_ddl()` is the single source of the layout: `create_schema()` executes exactly those statements and is idempotent (`IF NOT EXISTS` throughout plus `ON CONFLICT DO NOTHING` on the version row), and three tests freeze that — one scans every `.py` under `src/` and `tests/` for `CREATE TABLE|SCHEMA|VIEW|INDEX` heads and asserts the files containing one are exactly `schema.py` plus a visible `DDL_SCRATCH_FILES` exemption set, which a test file earns only by confining its DDL to throwaway probe objects that are never layout names (`tests/test_workspace_types.py` probes column types on tables it creates in-memory; `tests/test_workspace_lifecycle.py` plants foreign objects in throwaway files to pin that rw `open()` refuses a foreign database; equality rather than containment keeps a stale exemption from lingering); a second keys on the name each head *creates* — bare or schema-qualified, through the `IF NOT EXISTS`/`OR REPLACE` spellings — and forbids every file but `schema.py` from creating a layout name, derived from `EXPECTED_TABLES` plus the `meta` schema so a table added to `_DDL` is protected without a second list, which is what makes the exemption safe: a scratch file may create `t`, never `pkts`, and merely *querying* `pkts` is fine anywhere; the third counts the heads inside `schema.py` against those in `iter_ddl()` so no helper can build DDL inline. `naming.column_name` is the frozen abbrev → column policy, shared with #26 by import rather than restatement so the schema and type layers cannot disagree about column names: it keeps the **full** abbrev — no parent stripping, unlike `codegen/mangle.py`, where `tcp.port` safely shortens to `port` on `TCP`, because columns share one flat namespace inside `pkts` and `tcp.port`/`udp.port` must stay distinct — lowercases it because DuckDB compares identifiers case-insensitively (so `ip.Src` and `ip.src` *are* one column, and lowercasing surfaces that as a collision instead of a silent overwrite), maps non-ASCII-alphanumerics to `_`, and prefixes a leading digit with `f_`. Like the attribute policy it is **not injective** (`tcp.port` and `tcp_port` both yield `tcp_port`), so running `find_collisions` and refusing is mandatory before materializing a field set, not advisory; `ColumnNameCollisionError` is the exported type for that refusal, which `materialize.py` (#31) raises before it adds a single column, and storage backs the rule up with a `UNIQUE` on `meta.fields.column_name` so two abbrevs can never claim one column even if a caller skips the check. `naming.SKELETON_COLUMNS` names the two columns `pkts` is born with, reserved because they are already materialized: `find_collisions` cannot flag them (they collide with nothing), so `add_field_column` refuses them by name with "already the row key" rather than the generic duplicate-column message. Column types come from the caller and `types.py` is where callers get one; `schema.py` stays type-agnostic and never derives a column type from an ftype itself. A SQL type cannot be bound as a parameter, so `add_field_column` validates `sql_type` against a conservative pattern and quotes the column name; both its duplicate check and its `ALTER` are pinned to `main.pkts` / `current_database()`, because `duckdb_columns()` spans attached databases and would otherwise see a foreign table's column as a duplicate. Timestamps are UTC and never `TIMESTAMPTZ`, which DuckDB renders through the session time zone so one file would print different timestamps on different machines: DuckDB `TIMESTAMP` is timezone-naive, so aware datetimes are converted to naive UTC on write and re-tagged UTC on read, and a naive datetime handed in is taken to be UTC already. The `to_db_timestamp`/`from_db_timestamp` pair implementing that lives in `types.py` since #26 (it is `FT_ABSOLUTE_TIME`'s codec pair), and `schema.py` imports it for its catalog columns so the two layers cannot drift apart on the convention. `CacheKeyRecord.fields`/`.argv` are stored in native `VARCHAR[]` columns and read back as tuples, so #32's subset rule is a `list_has_all` predicate in SQL rather than a fetch-everything-and-decode scan, and the workspace file stays directly queryable. duckdb is the optional `remora[workspace]` extra (and part of `remora[all]`): every module here is import-pure — `DuckDBPyConnection` is annotated under `TYPE_CHECKING`, so importing the package never imports duckdb, and the one runtime import lives inside `workspace.py`'s connect helper, reached only when a connection is actually opened — and connections are caller-supplied everywhere outside `workspace.py`, because connection and lock ownership belongs to the `Workspace` class (#28). `SCHEMA_VERSION` (2 since #33 changed `streams`; 1 was every release up to #31) is written into `meta.info` at creation; a missing `meta.info` or missing version row means "not a remora workspace" (probed with `database_name = current_database()`, like the duplicate-column check, so an attached workspace cannot vouch for a blank current database), and `check_compatible` accepts only the exact version, naming both in either direction: there is no migration path, and an older file has to be refused loudly because `create_schema` is `IF NOT EXISTS`-only and would no-op on the stale tables. `create_schema` does not imply `check_compatible`; #28's opener must call both. `workspace.py` (#28) is that owner and the only module in the package that opens a connection: `Workspace(path, mode="ro")` is a context manager whose default is read-only because DuckDB's single-writer lock means one long-lived read-write connection blocks every other process's reads — ro mode holds one long-lived read-only connection (a shared lock, so concurrent readers are unaffected) while `rw` mode holds **no** connection between operations, `write()` opening a short-lived read-write connection around exactly one transaction (commit on clean exit, rollback on exception, close either way) so the exclusive lock is released promptly, and `read()` in rw mode opening read-write rather than read-only because DuckDB refuses two live same-process connections to one file with different configurations and a read may nest inside `write()`. That last concession has two consequences a caller has to know: an rw-mode read holds the exclusive lock for its whole duration, so a long read under `mode="rw"` locks other processes out exactly like a write does and a read-mostly caller wants `mode="ro"`; and a read nested inside `write()` runs on its own separate connection, so it does not see the enclosing transaction's uncommitted rows. Opening always runs `check_compatible`, and rw mode runs `create_schema` first only when the database holds no user objects at all — tables, views, sequences, macros, user types and schemas alike, each probed via `current_database()` like every other catalog probe, because a foreign database is not necessarily betrayed by a table and counting only `duckdb_tables()` let a view-only file be adopted and half-upgraded — so a foreign or stale file is refused instead; ro mode on a missing file is an error naming `mode="rw"`, and the write APIs in ro mode raise `WorkspaceModeError` saying the same thing. A checkpoint truncates only *trailing* free blocks, so emptying a table largely shrinks the file by itself while scattered deletes leave interior free blocks the file keeps forever — which is what `compact()` (rw only) exists for: it rewrites every schema, table and row into a sibling `<name>.compacting` temp file with `COPY FROM DATABASE` and swaps it in atomically with `os.replace`, so an interruption at any point leaves the original intact and at worst a stale temp file — plus the `.wal` sidecar a hard kill mid-copy can leave beside it, unlinked wherever the temp itself is — that the next compact removes. The rewrite runs on a read-write connection to the *source* (only the temp is attached, as `compact_dst`) and the `os.replace` happens while that connection is still open, so the source's exclusive lock is held across both the copy and the swap: another process's writer either commits before compaction begins — and is therefore copied — or fails fast on the lock until the swap completes, and no commit can land in a close→replace gap and be silently discarded, which is exactly what an in-memory connection with a read-only attach used to allow. The price is that every other process, readers included, is locked out from the moment the lock is taken *through the atomic rename* — the rename, not the return, is the cross-process linearization point, because it installs a new inode the old file's lock does not cover, so another process may connect the instant it lands, safely: such a write goes into the compacted file and survives (a pinned test commits one there), where same-process writers stay excluded until the source connection closes because an admit would join the pre-swap instance — and conversely compaction needs sole access, failing fast on DuckDB's lock error if any other process (a read-only reader included) is already connected, with nothing modified — and that a same-process `write()` or rw-mode `read()` shares this instance and would *not* hit the lock, which the file lock therefore cannot arbitrate: a module-level registry keyed by the file's **identity** — `(st_dev, st_ino)` from an `os.stat`, recomputed per operation and never cached because `compact()` swaps the inode, falling back to the resolved pathname only for a file that cannot be stat'ed — does it instead (plain counters and a flag, never a connection — the no-module-level-*connection* rule is about connections). Identity rather than pathname is the fix for a reviewer-reproduced hole: a `realpath` string preserves spelling, so on a case-insensitive filesystem `ws.duckdb` and `WS.DUCKDB` keyed differently and a second `Workspace` could commit *during* the swap and have it discarded — and a hard link did the same on every platform. Keying on the inode makes every spelling, symlink and hard link of one file coordinate as one — and because an identity key is exactly what `compact()` swaps, `compact()` holds its flag under **both** the old and the new identity (claiming the temp's the moment the temp is final, releasing both only *after* the source connection is closed) while writers re-stat the file once their slot is held and retry if the identity moved: without the first half a writer that stats the path after the `os.replace` finds no entry, is admitted, joins the pre-swap DuckDB instance (its cache keys on the *path*, which compact's source connection still holds) and commits into the file that was just thrown away — a second reviewer-reproduced silent loss — and without the second half a writer that stalls across an entire compact holds a slot under a dead key and no longer blocks the next one. `compact()`'s own claim gets the same treatment: another *process's* compact can swap the inode at any instant this one does not hold the file's exclusive lock, so the source connection is opened inside the claim loop and the identity re-checked while both the flag and the lock are held — no swap can happen under the lock, so a match proves the flag covers the live file for as long as the connection stays open, and a mismatch closes the connection, drops the flag and retries against the new file (a third reviewer-reproduced loss: a child-process compact completing in the claim-to-connect gap left the flag on a dead inode, and a same-process writer keyed on the live one was admitted mid-swap). Coordination follows file identity, so writes are locked out through every alias for a compact's whole duration, swap included. The registry keys being tuples is why `_acquire_write_slot`/`_begin_compact` take the `Path` alongside the key: the error messages name the path. The residual is inherent to atomic swap rather than a coordination gap: a hardlinked alias still points at the *old* inode once a compact through another name completes, so the two names diverge after a successful compact — never during one. That coordination makes `write()`/rw-`read()` and `compact()` mutually exclusive across every `Workspace` object and thread in the process, so `compact()` raises `WorkspaceError` on an in-flight body of *any* instance rather than swapping the file out from under it, a second concurrent `compact()` is rejected the same way, and for compaction's duration writers and rw-mode readers fail fast with `WorkspaceError` exactly as a second process fails on the file lock — the case a reviewer reproduced as silent data loss when the counter was per-instance. Cleanup of a stale `.compacting` temp and its `.wal` happens only *after* the exclusive lock is acquired, so a lock-conflicted `compact()` modifies nothing at all, another process's in-flight temp included — and that failed connect is wrapped too, so losing the lock (a second process, or an ro-mode `Workspace` on this file in *this* process, whose long-lived read-only connection DuckDB will not let a read-write one join) reads as a `WorkspaceError` about needing sole access rather than a raw duckdb exception. `compact()` also works on the path's `realpath`, not the path as given: a workspace addressed through a symlink is compacted at its resolved target, so the temp lands beside the real file and the swap replaces the real file, leaving the alias a symlink instead of turning it into an independent regular file (a *hard* link cannot be preserved that way — the replaced name gets the new inode while the other name keeps the old one — which is the documented residual above). The temp is a brand-new file, so it is born with umask defaults and would silently widen a `0o640` workspace to `0o644`; `compact()` therefore copies the source's mode bits onto the temp between the `DETACH` and the `os.replace`. Ownership and other metadata follow the fresh file, since `chown` needs privileges compact does not assume. The swap-under-lock design is **POSIX-only today**: Windows refuses a rename over a file the process holds open, so there `compact()` raises `WorkspaceError` naming the limitation (#85) instead of surfacing a bare `PermissionError`, and the original is left intact — and that wrapping is deliberately narrow, catching only `PermissionError` so any other `OSError` from the rename propagates as itself. duckdb is imported lazily inside the connect helper, which is what makes a module-level connection impossible (`tests/test_workspace_import_purity.py` deliberately carries no `importorskip`, so its fresh-interpreter check — no duckdb in `sys.modules`, and on Linux no file handle left open — and its missing-duckdb `ImportError` check run precisely where duckdb is absent), and a missing duckdb raises `ImportError` naming `pip install 'remora[workspace]'`. `types.py` (#26) is `values.py`'s other half: `values.py` owns raw tshark text → Python value, `types.py` owns that Python value ↔ what DuckDB stores, and nothing else in the tree maps an ftype to a SQL type. `COLUMN_TYPES` covers exactly `values.FTYPE_TABLE`'s ftype universe (a test asserts the two key sets are equal, so an ftype added there cannot silently fall out) and is **frozen** — a workspace written by one remora is read by the next, so changing a column type is a storage-format change, not a tweak. Addresses are stored as their integer form (`FT_IPv4` → `UINTEGER`, `FT_IPv6` → `UHUGEINT`) so subnet matching degrades to a `BETWEEN` over an ordered column that DuckDB's zone maps can skip row groups on (epic #43), where a text column would force a per-row parse; integer ftypes keep their exact width for the same reason, since a blanket `BIGINT` would cost 8x the bytes on `FT_UINT8` and widen every zone map's range. `FT_FLOAT` is `DOUBLE`, not `FLOAT`, because `values.py` parses it with `float()` to a Python double and `FLOAT` would round every value on the way in, making the round trip lossy; `FT_RELATIVE_TIME` is `INTERVAL`, which round-trips `timedelta` natively and dodges the usual month-component ambiguity because a `timedelta` never carries months (`avg`/`min`/`max`/`median` take an `INTERVAL` directly, but `sum` and `quantile_cont` do not, so #32 must route a total or a p95 through `epoch(v)`); `FT_ETHER` is `BLOB` because `values.py` yields 6 raw bytes rather than text; an unknown ftype falls back to `VARCHAR` with identity codecs, mirroring `values.get_info`'s fallback to `str`. There is no pyarrow dependency (nor a duckdb one — SQL types are plain strings and encoded values plain Python), but the module's table documents the Arrow equivalent per ftype for #31, along with the export hazard #31 must respect: DuckDB exports `UHUGEINT` through Arrow as `decimal128(38, 0)` read as **signed**, so every `FT_IPv6` address with the high bit set — all of `fe80::/10` link-local and `ff00::/8` multicast, i.e. essentially every real capture, not a top-of-the-range corner case — comes back two's-complement negative; the DuckDB-native path is exact (tests pin the addresses either side of 2^127), which is what keeps `UHUGEINT` the right column type — but that exactness is not free, and `FT_IPv6` is the one ftype whose encoder emits a **decimal string** rather than the `int` its column type suggests: DuckDB unifies a Python list's *inferred* element types before casting them to the column type, so an element below 2^63 (`::`) alongside one above 2^127 (`ff02::1:2`) unifies to signed `HUGEINT` and the bind fails outright, and an explicit `?::UHUGEINT[]` cast does not help because the unification happens first. A DAD Neighbour Solicitation puts exactly that pair into one `ipv6.addr` list, so #31 would hit it on ordinary traffic; `VARCHAR` casts to `UHUGEINT` in scalar and list position alike, so the column type, the read-back `int`, and `list_contains(v, <int>)` are all unchanged. No other ftype needs it — no other column type reaches 2^127 — so do not broaden it. `column_spec(abbrev, ftype, multi)` is the single per-field call #31 needs, pairing `naming.column_name` with the SQL type and codecs: a multi-value field's column is the scalar type's `LIST` (`T[]`), an absent scalar encodes to `None` and an absent multi to `[]` — never `NULL` in a list column, because `list_contains(NULL, x)` is `NULL` while `list_contains([], x)` is `false`, and `false` is what the predicate backend means by "an absent field never matches" (a `NULL` read back from a multi column still decodes to `()`, since a column added later back-fills `NULL` on older rows) — and a field declared scalar that occurs more than once in a packet raises `ValueError` rather than keeping the first and silently dropping data. `cachekey.py` (#27) computes what #32 later compares: `fingerprint_pcap` identifies a capture by `st_size`, `st_mtime_ns` and a sha256 over its first and last 64 KiB — never a whole-file digest, because materializing a multi-gigabyte capture must not first read it twice, and never the float `st_mtime`, because integer nanoseconds are exact and platform-stable. The sample digest deliberately excludes size and mtime so the three components stay separable in the rendered `fp1:size=…:mtime=…:probe=…` string, and it buys its cheapness with a real blind spot: an in-place edit to the middle of a large file that changes neither length nor mtime fingerprints identically, which a named test pins so it stays a known trade-off rather than becoming an incident. `make_cache_key` digests the rendered fingerprint, the projection field set, the dfilter, the tshark version and the **full effective argv** — verbatim and order-sensitive, because a different `-X lua_script:`, `-d` or `-o` dissects identical bytes into different fields, which is exactly the omission that makes a cache silently wrong. Components are length-prefixed before hashing so no argument boundary is ambiguous (`-rcap.pcap` cannot digest as `-r cap.pcap`), the field set is sorted and deduplicated so projection order never flips the key and #32's `list_has_all` subset test sees a canonical set, `None` and `""` dfilters digest differently, and the key carries a `ck1:` scheme prefix so a future change to the scheme invalidates stored keys visibly instead of sharing one namespace with a second scheme. `pcap_path` is stored for diagnostics but not hashed — argv already carries the path tshark was given. The digest is sha256 throughout and never `hash()`, so keys are stable across processes; a pinned golden digest and a subprocess run under a randomized `PYTHONHASHSEED` both guard that. The function returns #25's `CacheKeyRecord` rather than a bare digest precisely so the components that were hashed and the components that get written cannot drift apart. That pairing is also why the two layers hold different contracts: `_to_bytes` encodes with `surrogateescape` so hashing is total and can never raise, while `make_cache_key` separately refuses any component DuckDB `VARCHAR` cannot hold — a lone surrogate, which is what `os.fsdecode` yields for a non-UTF-8 POSIX path or argv element. Ordinary non-ASCII stores and round-trips fine; only the unstorable case is refused, with a `ValueError` naming the component, raised before the capture is read. Storing it losslessly instead would need a reversible text encoding of arbitrary bytes inside `VARCHAR`, which is a storage-format change and a `SCHEMA_VERSION` bump, so the boundary is drawn here rather than in #25.
  `materialize.py` (#31) is M4's tracer bullet — capture on disk → tshark `-T fields` → `main.pkts` plus the `meta.fields` and `meta.cache_keys` rows describing what landed — and it composes the four modules above rather than owning policy of its own. `Workspace.materialize` is the intended entry point (the module's `materialize_into`, `detect_tshark_version`, `MaterializeResult` and `TsharkRunner` are exported too, for callers holding their own connection) and is exactly one `write()` transaction wrapped around `materialize_into`, so rollback (every appended row *and* every `ALTER`-added column, which DuckDB rolls back with the rest) and prompt lock release are **inherited from #28, not reimplemented** — the price being that the exclusive lock is held for as long as tshark takes on the capture, which is also why the `tshark --version` probe carries a timeout: a hung binary must not own the file forever. A `filter` must compile all the way to a `-Y` display filter or the call raises `UnsupportedExprError`; unlike `planner.py` there is deliberately **no residual-predicate fallback**, because the cache key records only the dfilter, so rows selected half by `-Y` and half in Python would be stored as if the `-Y` alone had produced them and #32 would hand them to a query with a different residual. The projection always asks tshark for `frame.time_epoch`, never `frame.time`, which renders a human-readable locale- and timezone-shaped string where the epoch form is what `values.convert` parses for `FT_ABSOLUTE_TIME` into the `frame_time` skeleton column; correspondingly a caller *requesting* `frame.number` or `frame.time` gets no column of their own — the row key already holds that data — while those abbrevs still count in the cache key's field set, so #32's `list_has_all` subset test sees what was actually asked for. Rows are encoded through `ColumnSpec.encode_raw` and appended with plain-value `executemany` in batches bounded by `batch_size`, so memory stays flat on a capture of any size and the input is consumed lazily one batch at a time; Arrow record batches would be the obvious faster path and are refused on the `FT_IPv6` `decimal128(38, 0)`-read-as-signed hazard `types.py` documents, since the DuckDB-native bind path is exact. Both external dependencies are injectable seams so the unit suite never spawns anything: `TsharkRunner` is a `Callable[[Sequence[str]], TsharkRun]` naming the shape `reader.process.TsharkProcess` already has, so the pipeline itself spawns nothing and `Workspace.materialize` is what supplies the real class as the default, and `tshark_version` is a parameter rather than a probe, defaulted by `detect_tshark_version`, which reuses `codegen.fingerprint.parse_tshark_version` rather than re-parsing `tshark --version` a second way — imported inside the function body, so `import remora.workspace` never drags the code generator in for a parse only a probe performs.
  Reuse — hit, backfill or refuse (#32) — is decided here too, and it is what replaced #31's blanket refusal of a non-empty workspace. A workspace records exactly **one** `meta.cache_keys` row, describing the materialization `pkts` currently *is*, and a second `materialize_into` is decided against it **component by component, never digest against digest**: the stored digest covers the *requested* field set, so two requests differing only in their projection have different digests and comparing those would call every widening a mismatch. The components that must be identical are the capture fingerprint, the dfilter (`None` and `""` still distinct, as #27 digests them), the tshark version, and the argv **modulo the parts other components already own** — `-e` (owned by the field set), `-r` (owned by the fingerprint, which identifies a capture by its bytes, so the same capture moved or renamed is the same capture) and `-Y` (owned by the dfilter) — leaving argv[0] and every dissection-changing option (`-X lua_script:`, `-d`, `-o`) compared verbatim, which is exactly the omission that makes a cache silently wrong. With those equal the field set decides: requested ⊆ materialized is a **hit** that spawns no dissecting tshark at all (the `tshark --version` probe still runs when the caller omits the version, since that version is one of the compared components), tested as a `list_has_all` predicate in SQL (`schema.find_covering_cache_key`) — which is what #27's sorted-and-deduplicated field set and #25's native `VARCHAR[]` column were for — and anything more is a **backfill**. A backfill rescans, because tshark's dissection cost cannot be avoided, but it projects only `frame.number` plus the *new* fields, runs `find_collisions` over the **union** of stored and requested abbrevs before adding a single column (the naming policy is not injective, so a new abbrev can claim a column an earlier run already owns), and fills the new columns with `UPDATE main.pkts SET … WHERE frame_number = ?`, so no existing column is rewritten. Absent values are encoded exactly as a fresh run encodes them (`NULL` scalar, `[]` multi — the `NULL` that `ADD COLUMN` back-fills survives nowhere), and the recorded key is recomputed over the union field set with the argv the equivalent one-shot run *would* have used — which is why the projection is built in canonical abbrev-sorted order — so a workspace built incrementally is indistinguishable from one built in one go, digest included, and the superseded key row is deleted rather than accumulated. Since fingerprint and filter are unchanged the scan must produce the same *row-key set* `pkts` already holds — one row per stored frame number — which is checked as a **set** comparison and deliberately not as a count: a scan emitting one frame twice and another not at all has the right count while updating one stored row twice and leaving another at the `NULL` its `ADD COLUMN` back-filled, with the cache key recorded as if the backfill were complete. Each scanned row key is therefore staged in DuckDB and compared against `pkts` in four directions (scanned rows carrying no frame number at all, duplicates, scanned keys `pkts` does not hold, stored rows the scan never produced — the NULL case counted separately and excluded from the other three, since SQL equality never matches NULL and it would otherwise be reported as the symptom rather than the cause, having previously escaped as a bare `TypeError` from rendering `int(None)` inside the error path), refusing with up to five example frame numbers per kind and rolling the whole backfill back; staging in the database rather than a Python set is what keeps that exact *and* memory-bounded on a capture of any size, which is why `schema.py` grew a second DDL constant — `iter_scratch_ddl()`, a session-scoped `TEMP` table (`backfill_scan`, row key only, so no DDL is ever built from a caller's field set) that lives in DuckDB's `temp` database, is invisible to every `current_database()` catalog probe here, and dies with the connection. It sits beside `iter_ddl()` rather than inside it because it is DDL the module owns but the *layout* excludes; the schema tests count both, assert every scratch statement is `TEMP` and names nothing the layout owns, and their DDL-head regexes were widened to see the `TEMP`/`OR REPLACE` spellings they previously missed. What that set check establishes is **row alignment**, and precisely not that the capture's bytes are unchanged: value identity of the columns a backfill does not rescan rests entirely on #27's fingerprint, which is a sample rather than a whole-file digest. #27's named trade-off is therefore inherited here with a sharper consequence — an in-place middle edit preserving size, mtime and both sampled blocks is invisible (`tests/test_workspace_cachekey.py::TestFingerprint::test_middle_change_does_not_flip` pins the fingerprint half), and if it also preserves frame numbering the backfill commits new-field values read from the edited capture beside old columns read from the original, under a key that looks entirely valid. That is an accepted cache-integrity limitation, not an oversight: closing it would need either the whole-file digest #27 explicitly refused (a multi-gigabyte capture must not be read twice) or a re-projection of columns the backfill promises not to rewrite. `tests/test_workspace_cache.py::TestInheritedFingerprintBlindSpot` pins the consequence end to end rather than fixing it, alongside a companion test showing a *visible* edit still refuses, so the blind spot reads as narrow rather than as an absent check; the issue's acceptance criterion and `Workspace.materialize`'s docstring state the same narrowing, and a caller who cannot rule out an in-place edit should materialize into a fresh workspace file. A request adding only row-key-backed abbrevs (`frame.number`/`frame.time`) widens the key without any rescan and reports as a hit, so the next identical request decides nothing. Every other difference refuses with `MaterializationMismatchError` naming each changed component and pointing at a fresh workspace file — rematerializing in place would drop rows a caller may already have annotated (#30), so it stays future work — as does a request redeclaring a stored field's ftype or multiplicity, since the column type follows from those. Reuse is gated on the workspace being *intact*, checked in that order before any hit is served or any backfill delta sized: a workspace holding rows or registered fields but *no* cache key, or more than one key, is refused as not this pipeline's work; so is one whose stored key and `meta.fields` disagree about which fields are materialized; the subset rule reads the key alone, so a key claiming a field the registry does not register would answer a request for it with a *hit*, reporting stored data for a column the workspace may not hold. The two are written together in one transaction and must describe the same workspace (row-key-backed abbrevs excepted, since they get no column), checked in both directions and never repaired — which of the two states the truth is exactly what cannot be determined from there. And so is one whose declared shape disagrees with the *physical* table: a registry row is a description of `main.pkts`, not evidence about it, so every registered column — **and the two skeleton columns, which nothing registers and which were therefore the one part of `pkts` no check covered** — is verified against the live `duckdb_columns()` (pinned to `current_database()`/`main` like every other probe here, one read serving both) with the type it is declared under. The skeleton's declared types come from `schema.SKELETON_COLUMN_TYPES`, the single authoritative statement of what `frame_number`/`frame_time` are, which `materialize.py`'s `_FRAME_NUMBER_SPEC`/`_FRAME_TIME_SPEC` now read instead of restating; it sits beside `_DDL` rather than being parsed out of it, and drift is prevented executably instead — a test runs `create_schema` and asserts the live catalog reports exactly that mapping (and that its keys are `naming.SKELETON_COLUMNS`, since `naming.py` cannot import `schema.py`). Without the skeleton half, a dropped `frame_time` still answered a repeat request with a *hit* and a dropped `frame_number` surfaced as a raw DuckDB catalog error from inside the backfill's row-key probe, while a *retyped* `frame_number` was misdiagnosed by that probe as "rows with no frame number at all" — the symptom rather than the cause. The check also runs on the first-materialization path, which binds straight into those columns — otherwise a hit names a column that was dropped, and the caller's next query fails with a raw binder error far from the cause, or one recreated with another type is read back through the wrong codec. String equality is exact for the comparison because DuckDB reports back precisely the type `add_field_column` was given for every entry in `COLUMN_TYPES`, `T[]` list spellings included, which a test pins across the whole ftype table. A backfill additionally verifies the row key it is about to match on: `pkts` has no `PRIMARY KEY`, so `frame_number`'s uniqueness is convention, and a duplicate would make `UPDATE ... WHERE frame_number = ?` fan out one scanned row's values across several stored rows while a `NULL` one matches nothing — one statement of two aggregate passes over a single `BIGINT` column, run before any column is added or any row touched, and only on the backfill path, since a hit writes nothing and so cannot fan out. `MaterializeResult` carries the `outcome` (`"materialized"`/`"hit"`/`"backfilled"`), `fields` as the union after the call and `added_fields` as just what this call added.
  `export.py` (#34) is the way out: `Workspace.export_parquet(table, path)` writes one `main` table to one Parquet file as exactly one DuckDB `COPY ... TO ... (FORMAT PARQUET)` statement, so a table of any size streams to disk without a row passing through Python (the only other statements are two catalog lookups that touch no table — the column types the rewrites below are decided from, and the file backing the current database that the destination is checked against), and it is a read — one `read()` like `list_annotations`, so it works in `mode="ro"` and never opens a write connection. Parquet is the **export** format, never the storage format: it serves delivery, archival and downstream Spark/Athena ingestion while the live workspace stays DuckDB-native because it is mutable (annotations), and importing Parquet back in and partitioned dataset layouts are both out of scope. An export is a derivative and the pcap stays the source of truth: the file holds the table's columns and nothing else — no payloads, no field that was never projected into a column, no `meta` catalog — so a question about an unmaterialized field goes back to the capture. Neither a table name nor a path can be a bound parameter in `COPY`, so `table` is validated against the closed `EXPORTABLE_TABLES` set (`pkts`, `streams`, `annotations`) and refused otherwise — refusal, not escaping, is the only safe treatment for something that must reach SQL as an identifier — while the path is escaped for a single-quoted literal (a path containing `'` is a pinned test). The *destination* is checked too, for a blunter reason: `COPY` overwrites whatever is at the path, so an export aimed at the workspace is a deletion — reproduced before the guard existed, the database file became a 336-byte Parquet file and reopening it raised duckdb's `IOException`. All four spellings do it (the database path, a symlink to it, a hard link to it, and the `.wal` sidecar), and the `.wal` is the worst because it fails **silently**: DuckDB replays a write-ahead log on open, so a log overwritten with Parquet is discarded along with every committed row it still held and the database then opens without complaint (measured: 1999 rows down to 1, no error). So the destination is compared against the database file — read from `duckdb_databases()` rather than from a `Workspace` attribute, so a caller holding their own connection is covered too — and against its `.wal`, before the `COPY` runs, and a match raises `WorkspaceError`. The comparison is by file **identity** (`(st_dev, st_ino)`, the same rule `workspace.py` keys its coordination registry on, and the only one that sees through a symlink or a hard link), falling back to a resolved-pathname comparison when the destination does not exist yet — the normal case for the `.wal`. That check alone cannot carry the "under any spelling" guarantee, because it is check-then-act: `COPY` opens the path itself, so another process could plant a link to the database at the destination in the window between. The window is not closable by checking harder, so the write does not go to the destination at all — it goes into a private `0700` `mkdtemp` directory beside the destination, and `os.replace` renames the finished file out of it onto the destination. A rename replaces the directory **entry**: it never follows a symlink and never writes through a hard link, so a link planted after the check is simply replaced and the workspace inode is never opened (`_check_destination` stays, because a rename onto the database path would destroy it just as surely, and a caller who typed the wrong path deserves the error rather than the deletion). The directory, rather than a temp *file*, is what makes that airtight instead of merely likely: `mkstemp` picks an unguessable name, but the name is in the directory listing the moment it exists and DuckDB reopens it by name afterwards, so it can be swapped for a link in between — and what survives that today is DuckDB's incidental habit of unlinking its destination first, an implementation detail rather than a promise (measured both ways). Inside a `0700` directory no other user can enter at all, so the path `COPY` opens cannot be tampered with. The same rename buys destination atomicity the direct write did not have: a `COPY` that failed partway used to leave a truncated file where a good export had been, and now leaves the previous file exactly as it was, temp directory removed. Two residuals are stated rather than implied: the destination's own **directory is trusted** — anyone who can write there can rename anything onto the destination name whether remora writes there or not, and `0700` keeps other users out of the temp directory while a same-user process is inside the trust boundary already — and an external process moving the actual database file *onto* the destination path mid-export is not defended against, being the same thing as moving a live database out from under any writer. Types pass through as themselves — `UINTEGER` IPv4 stays unsigned `uint32`, narrow ints keep their width, `TIMESTAMP` is `timestamp[us]`, `BLOB` is `binary`, and a multi-value `T[]` stays `list<T>` — with exactly two divergences from the stored schema — two for any schema remora wrote, since `TEXT_EXPORTED_TYPES`'s third entry, signed `HUGEINT`, is defensive cover for a column some other tool added and no ftype maps to it — because DuckDB's Parquet writer cannot represent them and a silent corruption is worse than a documented type change. `UHUGEINT` (`FT_IPv6`) is the first: the Parquet path is *worse* than the Arrow `decimal128(38, 0)`-read-as-signed hazard `types.py` documents, because duckdb 1.5.5 writes 128-bit integers as a **`double`** — 53 mantissa bits for a 128-bit address, so `7fff:ffff:ffff:ffff:ffff:ffff:ffff:ffff` and `8000::` land on one value and nothing is recoverable, not even mod 2^128 — so the column is cast to `VARCHAR` and ships as exact decimal text, which is not a new invention but the same representation `types._ipv6_to_decimal_text` already binds IPv6 with (`IPv6Address(int(text))` or `CAST(col AS UHUGEINT)` reads it back). `INTERVAL` (`FT_RELATIVE_TIME`) is the second: Parquet's own interval logical type is millisecond-resolution, so a native write truncates 1234us to 1000us, and the text form (`'00:00:00.001234'`) is exact and casts straight back. Both rewrites apply at list depth too, so `UHUGEINT[]` exports as `list<string>`. pyarrow is deliberately **not** a runtime dependency of any extra — the export needs duckdb alone — and lives in the dev group only, where the round-trip tests read the file back and `pytest.importorskip` skips them gracefully without it.
  `annotations.py` (#30) is the mutable half of the workspace — the reason it is DuckDB native storage and not immutable Parquet — and it was built on #25's `main.annotations` columns exactly as they stood (`annotation_id`, `scope`, `target_id`, `key`, `value`, `created_at`), renaming and retyping nothing, so #30 itself cost no `SCHEMA_VERSION` bump; the table's seventh column, `protocol`, arrives with the v2 layout in #33, which is what made a stream annotation's target a *pair* (see below). Like every module here but `workspace.py` it takes a caller-supplied connection and opens none of its own, and unlike `cachekey.py`/`materialize.py` it does no file or process I/O either; the user-facing entry points are five thin `Workspace` methods (`add_annotation`, `remove_annotation`, `remove_annotations`, `delete_orphan_annotations`, `list_annotations`) that are each exactly one `write()` transaction — or one `read()` for listing, which is why listing works in ro mode while the four write methods get `WorkspaceModeError` from `write()` itself, and why no connection is held between calls. A **stream** annotation names its target by `(protocol, target_id)`, not a bare id, because that is the pair `main.streams` is keyed by since #33 — tcp and udp each number their conversations from zero, so `stream_id` alone names two rows. `add_annotation` therefore *requires* `protocol` for `scope="stream"` (`ValueError` naming `('tcp', 'udp')`) and *refuses* it for `scope="packet"`, where `frame_number` is unique on its own; the `main.annotations.protocol` column that stores it is the second half of the v2 layout, added by #33 rather than #30 because #33 is what made the pair a key. Matching on the id alone was a real bug, not a theoretical one: an annotation on a missing udp stream 0 read as **live** whenever a tcp stream 0 existed, so `delete_orphan_annotations` preserved it (`tests/test_workspace_annotations.py::TestStreamIdentity` pins both directions). `list_annotations`/`remove_annotations` take a `protocol` filter for the same reason, and it counts as a filter on its own for `remove_annotations`' no-unfiltered-wipe rule. A packet annotation is keyed by frame number alone because `pkts` has no capture column: `frame_number` is its row key, so one workspace holds one capture and the *file* is the capture identity, with `meta.cache_keys` (`pcap_path`/`pcap_fingerprint`) recording which capture that is; a multi-capture workspace would need a capture column in `iter_ddl()` and a `SCHEMA_VERSION` bump. `annotation_id` comes from a monotonic high-water mark stored in `meta.info` under `next_annotation_id` rather than from a sequence or from `max(annotation_id) + 1`: a sequence is unavailable because `create_schema` is `IF NOT EXISTS`-only and runs only on an empty database, so an existing workspace could never acquire one added later, while `max+1` was both non-unique and non-monotonic — 20 same-process threads each in their own `write()` transaction all committed id 1 (DuckDB's file lock serializes writers across processes but not within one), and deleting the highest-numbered annotation freed its id for the next add to reuse, so a stale id came to name — and `remove_annotation` to delete — a different finding. `meta.info` is the generic key/value catalog table every v1 workspace already has, so the allocator needs no layout change and no `SCHEMA_VERSION` bump; the mark is read and advanced inside the caller's transaction alongside the annotation row, so the id a commit used is never handed out again (a deleted id is gone for good and a stale one now matches nothing, returning `False`) and two racing same-process transactions both write that one row and DuckDB refuses the loser loudly — `duckdb.TransactionException` when both update an existing mark, `duckdb.ConstraintException` on `meta.info`'s primary key when both seed a missing one — rolling its whole add back instead of silently sharing an id. A workspace written before the key existed has no mark, and the seed path splits on whether it holds rows: an **empty** `main.annotations` — the only state a real upgraded file can be in, since every v1 file released remora wrote predates this API — is seeded silently and the first add returns 1; a table that **does** hold rows is refused with `WorkspaceError` and nothing is modified, because an id issued and later deleted leaves no trace, so no seed computed from the survivors (`max(annotation_id) + 1` included) can be proven to exceed every id ever issued, and the caller must instead set the mark by hand to a value they know is safe (`INSERT INTO meta.info (key, value) VALUES ('next_annotation_id', '<N>')` inside `Workspace.write()`). The orphan policy is **kept-but-flagged**: annotations are analyst findings, so a re-materialization under a narrower filter never deletes them — `list_annotations` derives `AnnotationRecord.orphaned` at read time (an EXISTS against `pkts`/`streams` rather than a LEFT JOIN, because `pkts` has no `PRIMARY KEY` and a join would fan one annotation out on a repeated frame number; the stream branch matches `(protocol, stream_id)`, and a stream annotation with a NULL protocol — unreachable through the API — reads as orphaned, since `s.protocol = NULL` is NULL), a wider filter un-orphans them again, and `delete_orphan_annotations` is the one explicit call that removes them. `remove_annotations` refuses a call with no filters, because wiping every finding is too destructive to be what zero arguments means.
  `streams.py` (#33) is sessionization — the headline capability a display filter cannot express, since a filter selects packets where this *aggregates* the conversation each one belongs to — and it is one set-based `INSERT ... SELECT ... GROUP BY` over `pkts` per protocol, never a Python loop over rows. The user-facing entry point is `Workspace.build_streams()`, exactly one `write()` transaction (so ro mode gets `WorkspaceModeError` from `write()` itself, and no connection is held between calls); the module takes a caller-supplied connection like every sibling but `workspace.py`, and does no file or process I/O at all. One row per **`(protocol, stream_id)`** pair, because tcp and udp each number their streams from zero — the stream id alone is not a key, which is why a packet joins back on both columns — and the row carries the endpoints, `first_frame`/`last_frame`, `pkt_count`, `byte_count` and `first_time`/`last_time` (the duration is the difference). Endpoints are read from the stream's **first frame by frame number**, all four in one `first(... ORDER BY frame_number)` aggregate so they describe one packet rather than a mix of directions: `src` is the initiator and `dst` the responder, matching the A/B ordering of tshark's own `-z conv` table, and a reverse-direction packet later in the stream never flips them. `#33` added the four endpoint columns and a `UNIQUE (protocol, stream_id)` key to `iter_ddl()`'s `streams` and therefore took `SCHEMA_VERSION` to **2**: a placeholder nobody had populated is still a layout change, because `create_schema` is `IF NOT EXISTS`-only and cannot graft the new columns onto an existing file, so a v1 workspace that still passed `check_compatible` would fail later as a raw DuckDB binder error inside `build_streams()` rather than as the documented loud refusal at open — `tests/test_workspace_lifecycle.py` pins the refusal, building its v1 file by `create_schema` + `ALTER TABLE ... DROP COLUMN` + a version downgrade rather than by hand-writing the old DDL, since Rule B forbids any file but `schema.py` from creating a layout name. `streams` keeps a key where `pkts` refuses one because it is on the catalog side of that trade — one row per conversation, not per packet, and rebuilt wholesale rather than bulk-appended — and the rebuild's delete-then-reinsert of the same keys inside one transaction is accepted by DuckDB (pinned, since an index still holding the deleted keys until commit would reject it). It hand-writes the endpoint SQL types (`UINTEGER`/`USMALLINT`) because `schema.py` stays type-agnostic, with a schema test pinning them against `types.column_sql_type("FT_IPv4")`/`("FT_UINT16")` so the endpoint columns can never drift from the `pkts` columns they roll up: addresses are the same `FT_IPv4` integer, so `s.src_addr = p.ip_src` is a plain integer comparison and no second representation exists. `byte_count` is the sum of **`frame.len`** — the packet's length on the wire, link-layer header included — deliberately the definition tshark's conversation statistics use for their Bytes column, and *not* payload bytes or `ip.len`; `tests/integration/test_streams_integration.py` parses a live `tshark -q -z conv,tcp`/`conv,udp` run and compares endpoints, frames, bytes and duration conversation by conversation, which only agrees if the byte definitions match. The prerequisite rule is **all of `REQUIRED_FIELDS`, both protocols', or nothing**: the nine abbrevs the SQL reads (`frame.len`, `ip.src`, `ip.dst`, and each protocol's `.stream`/`.srcport`/`.dstport`) are checked against `meta.fields` *before* any SQL touches `pkts`, and a gap raises `MissingStreamFieldsError` (a `WorkspaceError` carrying `.missing`) naming the exact abbrevs to add to `materialize()`'s field set — never a DuckDB "column not found". Validating each protocol independently and building whichever one's fields were present was the tempting alternative and is worse: a capture with no udp packets would build "successfully" and the omission would surface only on the next capture. The registry is also what tells the module whether a column is scalar or a `LIST`, since a prerequisite materialized multi-value (`ip.src` dissects twice on a tunnelled packet) is read at occurrence one, the outer header; **addresses are IPv4-only, and NULL is the signal**: `src_addr`/`dst_addr` come from `ip.src`/`ip.dst`, so they are NULL *exactly* when the stream's first frame carries no IPv4 header — an IPv4 frame always yields both (they are fixed header fields), and a frame too damaged to yield them is also too damaged to be given a stream index (a truncated IPv4 packet whose transport header is cut off gets no `tcp.stream` at all), so a NULL address never means "IPv4 packet missing one" and needs no extra discriminator column to say so. The **ports are unaffected**, since `tcp.srcport`/`udp.srcport` are transport-layer fields: an IPv6 stream's row carries real ports, stream id, counts and timestamps and only lacks addresses, which is why such rows are kept rather than dropped and `WHERE src_addr IS NOT NULL` is the documented way to select the fully-addressed ones. Real IPv6 address support would need `ipv6.src`/`ipv6.dst` in the prerequisites, `UHUGEINT` columns and an address-family discriminator to separate the two integer spaces — a storage-format change, tracked as a follow-up rather than smuggled into #33. Rebuilding is a whole-table `DELETE` plus the inserts inside the caller's one transaction, which is what makes it idempotent: one workspace holds one capture (the file *is* the capture identity, exactly as for annotations), so a rerun after a re-materialization replaces the rollups instead of duplicating them and drops streams whose packets are gone, and no reader ever sees the table empty. Stream *annotations* read as orphaned until `build_streams()` has run, since `annotations.py` derives orphanhood from an EXISTS against `main.streams`.
  `query.py` (#35) is the cache-side query surface, and it is a **separate class from `Capture` on purpose**: one `Expr` IR, two surfaces, so the type of the object in hand says whether a caller is paying for a tshark subprocess per iteration or a DuckDB scan over columns dissected once. `Workspace.query()` is the entry point and `Query` is immutable and chainable like `Capture` — `filter(*terms)` ANDs onto the existing terms and `select(*fields)` adds to the projection, both returning a new `Query`, and nothing touches the database until `__iter__`, `arrow()` or `sql()`. Every field the query mentions — every `FieldRef` in the filter tree (walked with `expr.field_refs`, deduped by `.name` because refs are unhashable by design) plus every `select()` argument — is checked against `meta.fields` **before** `compile_sql` runs and before any generated SQL reaches DuckDB, so a field nobody materialized reads as `field ip.src is not materialized — re-materialize including it` (`FieldNotMaterializedError`, every missing field named, never a raw `column not found`); `naming.SKELETON_ABBREVS` — `frame.number`/`frame.time`, factored out of #31's private copy so the two layers cannot drift — is exempt from the *catalog lookup* only, because those are the `pkts` row key and carry no registry entry. Exempt from the lookup is **not** exempt from the projection, and conflating the two was a reviewed defect: the row key is now a pair of ordinary `ColumnSpec`s (`_ROW_KEY_SPECS`) at the head of every projection, so it decodes through the same codecs as any other column and `row.get(<frame.number ref>)` reaches it under any `.select()` — where before it raised `FieldNotProjectedError` advising a `.select()` that failed identically. `frame.time_epoch` is deliberately *not* a skeleton abbrev: it is the abbrev #31 asks tshark for, and a caller requesting it gets an ordinary column. The same validation pass compares each ref's ftype/multiplicity against the stored declaration and refuses a disagreement with `FieldDeclarationMismatchError` naming both sides: such a ref compiles a predicate against the wrong column shape, which surfaces either as a raw duckdb `ConversionException`/`BinderException` or — when the wrong ftype happens to encode to something the column *can* hold — as a **silently wrong row set** (a reviewer found `frame.number` declared `FT_IPv4` coercing `"10.0.0.1"` to 167772161 and quietly matching nothing), so this is the missing-field rule applied to version skew between a workspace and the protocol modules querying it. Refs are deduped by the `(name, ftype, multi)` triple rather than by name, so a good ref earlier in a query cannot mask a stale one later. The rule lives in one function (`_declaration_mismatch`) and is applied in **two** places, because a ref is a static type as much as a column address: at compile time, and again in `Row.get`/`get_all` — a name-only lookup there returned an `IPv4Address` through an accessor mypy had typed `str | None`, and reported a multiplicity disagreement as the caller's *accessor* being wrong rather than their declaration. The two failures stay distinct: `FieldDeclarationMismatchError` means the ref disagrees with storage, `ValueError` means the ref agrees and the accessor is the wrong one. The row key is the only carve-out and only on ftype, via a **closed** accepted set (`_ROW_KEY_FTYPES`): `frame.number` takes `FT_UINT32` (`-G fields`' own declaration) or `FT_FRAMENUM` (#31's insert-side spec) because both resolve to `UINTEGER` with identity codecs and neither can encode or decode differently, `frame.time` takes `FT_ABSOLUTE_TIME` alone as the only ftype mapping to `TIMESTAMP` with the `to_db_timestamp`/`from_db_timestamp` pair the column is written and read with, and an ftype that merely shares a column type (`FT_UINT24` is also `UINTEGER`) is refused because nothing here declares the row key that way. Multiplicity is never carved out. The catalog is also what **decoding** follows: a row's `ColumnSpec` is rebuilt from the stored `FieldRecord` (abbrev, ftype, multiplicity, column type), never from the caller's ref, so read-back always matches what was written, while the ref's ftype still governs literal *encoding* inside `compile_sql` — the declaration check is what keeps the two from disagreeing. `UnsupportedSqlExprError` (a `matches` pattern RE2 cannot run or cannot agree about, `contains` on BLOB) propagates as itself — a statement about the backend, not about the workspace. Parity with the pcap path is compared filter by filter in `tests/integration/test_query_parity.py`, and since #36 it holds for a negated comparison on a *scalar* column too (`~(f == v)`, the DSL's `!=`): what compiled to `NOT (col = ?)` — `NULL`, and so false for a packet missing the field, where Wireshark and the predicate backend include it — now carries #36's `coalesce(<leaf>, FALSE)`, and that case is the issue's named regression test; multi-value columns never diverged, since an absent one is `[]` rather than `NULL`. Iteration yields `Row`, and here the cache path **deliberately diverges** from `pkt[IP].src`: protocol views are defined over raw tshark text, a stored row has none (an `FT_ETHER` column holds bytes, an `FT_ABSOLUTE_TIME` column a timestamp), and re-rendering values as tshark would have printed them is a lossy round trip nobody needs — so `Row` is not a `RawPacket` and access is by field ref, `row.get(IP.src) -> T | None` and `row.get_all(TCP.port) -> tuple[T, ...]`, the descriptor contract's exact shapes with multiplicity checked at access time (`get` on a multi field raises rather than dropping occurrences, mirroring `Field`'s refusal of a multi ref) and `FieldNotProjectedError` reused for a materialized-but-unprojected field. The row key is always projected first, `frame_time` re-tagged aware-UTC through `from_db_timestamp` (raw SQL over `pkts` still sees the naive form), and results are ordered by `frame_number`; `__iter__` `fetchall()`s inside one `read()` block and decodes lazily afterwards, so a half-consumed iteration holds no connection — and in rw mode no write lock. That is **deliberately not streaming**, and the docstring states the trade-off rather than hiding it: paging with `fetchmany` would keep the connection open across the *consumer's* loop, which in rw mode holds DuckDB's exclusive lock for an arbitrarily long caller-controlled window on a query that only reads, and in ro mode rides the one held connection — `con.execute()` returns the connection, not an independent cursor — so a nested query would replace a paged result and silently return the wrong rows. The cost is peak memory proportional to the result set's raw tuples; the docstring points oversized results at `arrow()` or at the connection `read()` already hands out. `arrow()` returns a `pyarrow.Table` and is the one place #26's `UHUGEINT`-through-Arrow hazard is *acted on* rather than only documented: DuckDB exports it as `decimal128(38, 0)` read as **signed**, so every `FT_IPv6` address with the high bit set would come back two's-complement negative, and silent numeric corruption is the worst outcome for an analytics export — so `UHUGEINT`/`UHUGEINT[]` columns are cast to `VARCHAR` in the SELECT list, exact decimal text that `IPv6Address(int(text))` recovers. The **stored** type is untouched (a read-time projection, not a storage change) and nothing else is cast; the DuckDB-native iteration path still decodes straight to `IPv6Address`. pyarrow ships as its **own** extra, `remora[arrow]`, deliberately not folded into `workspace`: duckdb names pyarrow only under duckdb's *own* `all` extra, so `remora[workspace]` installs duckdb without it, and a workspace user who never exports to Arrow should not carry a ~35 MB wheel — a reviewer caught `arrow()` being unreachable from the documented install when the dependency was dev-group-only. `remora[all]` is the derived union, so it covers both (`tests/test_packaging.py` computes that union rather than listing it, and its closed-world set now names `workspace` and `arrow` as the two extras exempt from the `remora-<extra>==<version>` shape). `arrow()` converts a missing pyarrow into an `ImportError` naming the extra, exactly as `remora.proto.__getattr__` does for a missing protocol distribution, and every other `Query` operation works without it; the call prefers `to_arrow_table()` and falls back to `fetch_arrow_table()`, because duckdb ≥ 1.4 renamed it and changed `arrow()` to return a `RecordBatchReader`. Read path only: every execution goes through `Workspace.read()`, so `Query` works in ro mode and **never enters the write API and never writes** — no `write()` call, no DDL, no DML, pinned by a test that monkeypatches `Workspace.write` to raise and runs every operation. The guarantee is deliberately about the API, not the connection's configuration: rw-mode `read()` yields a read-write-*configured* connection by #28's same-process rule, and what `Query` issues on it is `SELECT` either way. Import purity holds as everywhere here (duckdb under `TYPE_CHECKING`, no module-level connection), with one wrinkle: `compile.sql` imports this package's `naming`/`types`, so `query.py` imports the *module* (`from remora.compile import sql as _sql_backend`) rather than binding `compile_sql` by name, which would fail whenever `remora.compile.sql` is the import entry point. Raw SQL passthrough, cross-capture `ATTACH` and aggregate/window helpers are out of scope by design — `Workspace.read()` already hands out the connection.

Cross-cutting invariants:

- `tests/test_proto_seed.py` pairing tests are the frozen-format contract, running against all generated core modules (reshaped in #19 when the generated tree replaced the hand-written seeds) — from here on, keep them passing unmodified.
- Attribute names come from the frozen mangle policy (`src/remora/codegen/mangle.py`) at generation time; `_table_` stores the full tshark name precisely so nothing at runtime may re-derive tshark names from attribute names or vice versa.
- Absence is `()` from `get_raw`, `None` from scalar instance access, `()` from multi instance access — never an exception (except `FieldNotProjectedError` for fields outside a `-T fields` projection).
- Underscore-prefixed attributes on protocol classes are reserved; ruff RUF012 requires the `ClassVar[FieldTable]` annotation on tables.
- `tests/conftest.py` provides `FakePacket`, the standard `RawPacket` test double.
