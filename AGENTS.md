# AGENTS.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Remora is a type-safe Python DSL for Wireshark/tshark capture analysis. It drives tshark subprocesses directly (no pyshark): field access is statically typed via `.pyi` stubs, display filters are built from expression trees instead of strings, and predicates are pushed down to tshark where possible. Work is organized by milestone epics (#40 M1 kernel, #41 M2 codegen, #42 M3 polish, #43 M4 DuckDB workspace); each epic issue defines the execution path and dependency graph.

## Commands

Everything runs through uv (Python ≥3.10; CI matrix is 3.10–3.14):

```bash
uv sync                                        # install deps
uv run pytest                                  # full test suite
uv run pytest tests/test_planner.py -v         # one file
uv run pytest tests/test_fields.py::TestScalarInstanceAccess::test_static_types -v  # one test
uv run pytest -m "not integration"             # skip tests needing a real tshark binary
uv run mypy --strict src tests                 # typecheck (tests included — this is the CI gate)
uv run ruff check .                            # lint
uv run ruff format --check .                   # format check (also formats code fences in docs/*.md)
```

The CI gate is all four: `ruff check`, `ruff format --check`, `mypy --strict src tests`, `pytest`. Run the full gate before committing.

Static typing assertions are part of the test suite: `assert_type(...)` calls in `tests/` are no-ops at runtime and are verified when mypy checks the test files. Beware that a preceding `assert x == value` can narrow a type and break a later `assert_type` — put `assert_type` before runtime asserts.

## Workflow

- One PR per issue. Branch `feat/issue-<n>-<slug>` (or `feat/<n>-<slug>`), PR body includes `Closes #<n>`. PRs are squash-merged, so merged local branches need `git branch -D`.
- **Process artifacts are issue comments, not repository files.** Design docs, specs, implementation plans, and progress notes go into the issue as `gh issue comment <n>` — they belong to the issue's history, not to the shipped tree. Only durable documentation (`docs/*.md`, ADRs, `AGENTS.md`) is committed. `docs/superpowers/` is gitignored scratch space — anything under it is local to one checkout and is not part of the tree.

## Architecture

Data flow for a query: **Expr IR → planner → tshark argv → reader → RawPacket → protocol view / predicate**.

- `src/remora/expr.py` — immutable expression IR, deliberately a leaf module (imports nothing from remora). Comparisons on fields build `Expr` trees via `FieldExprOps`; `__bool__` raises so `and`/`or`/chained comparisons fail loudly (use `&`/`|`/`~`, parenthesize comparisons). There is **no `Ne` node**: `!=` builds `Not(Comparison(EQ, ...))`, making Wireshark's multi-value `!=` pitfall unrepresentable. `FieldRef`s are intentionally unhashable (`__eq__` returns an `Expr`); dedup by `.name`.
- `src/remora/values.py` — the single source of truth mapping tshark ftypes (`"FT_IPv4"` …) to Python types and parse functions. Parse errors raise `ValueError` (loud beats silent); unknown ftypes fall back to `str`. `coerce_literal` normalizes user literals at compile time for both backends.
- `src/remora/fields.py` — the contract hub. `RawPacket` is the minimal packet protocol: `get_raw(name) -> tuple[str, ...]` with `()` meaning absent. `Field`/`MultiField` are dual-mode descriptors: class access (`IP.src`) returns a `FieldRef[T]` for building expressions; instance access (`pkt[IP].src`) returns `T | None` (scalar) or `tuple[T, ...]` (multi). Multiplicity is encoded in the descriptor *class* because `@overload` can only express the return type per class.
- `src/remora/compile/` — two backends lowering `Expr`: `dfilter.py` renders Wireshark display-filter strings (raises `UnsupportedExprError` for what it can't push; `!=` always renders `!(f == v)`), `predicate.py` compiles Python predicates over `RawPacket` (the end of the fallback chain — mirrors Wireshark semantics exactly, including any-occurrence matching on multi-value fields).
- `src/remora/planner.py` — two-level pushdown, pure decision, never spawns tshark. Pushable conjuncts become a `-Y` display filter; statically known field sets enable `-T fields` projection; opaque lambdas force `-T ek` whole-packet fallback. Failed-to-push `Expr`s become residual Python predicates.
- `src/remora/reader/` — `process.py` owns tshark subprocess lifecycle only (stderr drained by a daemon thread to avoid pipe deadlock; `close()` terminates/kills/reaps so no orphans). `fields_reader.py` parses `-T fields` output using literal `0x1f`/`0x1e` separator bytes embedded in argv (tshark has no hex-escape separator syntax). `ek_reader.py` parses `-T ek` NDJSON; ek key mapping is `layers["ip"]["ip_ip_src"]` (layer + `_` + dots→underscores).
- `src/remora/proto/` — protocol classes. `_meta.py` defines the **frozen compact-table format**: classes set only `_proto_` and `_table_: ClassVar[FieldTable]` mapping attr name → `(tshark_name, ftype, multi 0/1)`; descriptors are materialized lazily on first access (`ProtocolMeta.__getattr__` for class access, `ProtocolBase.__getattr__` for instance access) so a 10k-field module imports for free. Protocol modules are generated artifacts (#19): `codegen.toml` lists the core set and the curated multi-value fields; regenerate with `uv run python -m remora.codegen write` under the pinned tshark (in practice inside docker: `ubuntu:24.04` + `ppa:wireshark-dev/stable`, since the pin tracks CI's PPA; always pass `--platform linux/amd64` regardless of host CPU, because the fingerprint's `env:` line hashes the raw `tshark -G plugins` dump and that dump embeds multiarch paths (`x86_64-linux-gnu` vs `aarch64-linux-gnu`), so the committed hashes only reproduce on CI's amd64 architecture). `codegen.toml` also assigns extras-only protocols (`[extras.wireless|industrial|telecom]`) to the separate `remora-<extra>` distributions under `packages/` — each ships only leaf `remora/proto/<name>.py`/`.pyi` modules that graft into core's `remora.proto` at install time (`pkgutil.extend_path` merges editable/mixed installs); `remora.proto.__getattr__` imports installed extras lazily and raises an `ImportError` naming the extra (`pip install 'remora[wireless]'`) for missing ones; the generated `_extras.py` module→extra map stays in core next to `_meta.py`/`__init__.py`, and `write`/`check` cover every destination (`--packages-dir`); `remora[all]` means everything — the union of every other extra, protocol or not, which since #25 includes `workspace`'s duckdb (`tests/test_packaging.py` derives the union rather than listing it, and the CI `wheels` job therefore resolves `remora[all]` with `--find-links dist` instead of `--no-index`, since duckdb comes from PyPI) — all dists share core's version with exact pins, and the CI `wheels` job spot-checks built-wheel contents, the core-only `ImportError`, `remora[all]` resolution, and stub resolution. Each generated `.py` has a sibling `.pyi` stub that shadows it for type checkers, declaring `Field[T]`/`MultiField[T]` per attribute; `_meta.py` and `__init__.py` are the only hand-written files, ruff ignores E501 under `proto/` and the formatter skips the tree so committed bytes stay emitter-exact.
- `src/remora/codegen/` — the M2 generator's front and back halves. `parse.py` turns a `tshark -G fields` dump (`P`/`F` records) into frozen model dataclasses (`Protocol`, `FieldDef`, `FieldDictionary`); malformed, unknown, and duplicate lines become collected `ParseWarning`s (first occurrence wins) rather than silent drops. `mangle.py` is the frozen field-abbrev → attribute-name policy the emitter (#14) must follow; it is **not injective** (dots and hyphens both become `_`), so emitters must detect per-protocol duplicate mangled names. `tests/data/g_fields_sample.txt` is a checked-in subset of a real 4.6.7 dump (regenerate with `tests/data/make_g_fields_sample.py`); tests assert exact record counts against it. `emit.py` is the back half: `emit_protocol(protocol, fields, multi)` renders one protocol's paired `.py` (compact `_table_`, import-pure) and `.pyi` (one `Field[T]`/`MultiField[T]` attr per field) sources, byte-deterministic in input field order (reproducible bytes therefore require the canonicalized dump order from `fingerprint.py`, #68); multiplicity has no `-G fields` signal so the multi-abbrev set is caller-supplied, mangled-name collisions resolve first-wins — except that a data field displaces an earlier `FT_NONE` expert/structural marker (presence-only, no extractable value) for the shared attr name — and every collision path records an `EmitWarning`, and `mangle_protocol` (lowercase, non-alnum→`_`, digit→`p_` prefix, keyword→trailing `_`) names the module, upper-cased for the class. The contributor-facing procedures for all of this — Docker regeneration recipe, drift-check triage table, `psdsl gen` worked example — live in `docs/codegen.md`; the two describe the same machinery, so a change to one belongs in the other.
- `src/remora/workspace/` — the M4 DuckDB workspace. It owns the storage layout and catalog (#25) and, since #28, the `Workspace` class that owns *all* connection, lock and compaction policy: every other module here is layout, naming or codec logic that takes a caller-supplied connection and performs no I/O of its own. `cachekey.py` is the single exception and a narrow one: it reads the **capture**, never the workspace file, because a fingerprint is by definition a function of the capture's bytes — it opens no DuckDB connection and holds none of the lock, so connection ownership still belongs entirely to `Workspace`. Packet data lives in `main` (`pkts`, `streams`, `annotations`), the catalog in a dedicated `meta` schema (`meta.info` key/value including `schema_version`, `meta.fields`, `meta.cache_keys`), so `meta.fields` is a literal table reference and user SQL over `pkts` never trips on catalog names. `pkts` is created with only the row-key skeleton (`frame_number`, `frame_time`) — projected field columns are grafted on later by `add_field_column` — and deliberately has **no `PRIMARY KEY`**: DuckDB backs one with an ART index that taxes exactly the bulk append path #31 must keep cheap, so `frame_number` is the row key by convention (unique, ascending in capture order) rather than by constraint; the small catalog tables do keep their keys, because they take single-row writes and the constraint is the point. `streams` (#33) and `annotations` (#30) are documented placeholders — columns now, semantics there. `iter_ddl()` is the single source of the layout: `create_schema()` executes exactly those statements and is idempotent (`IF NOT EXISTS` throughout plus `ON CONFLICT DO NOTHING` on the version row), and three tests freeze that — one scans every `.py` under `src/` and `tests/` for `CREATE TABLE|SCHEMA|VIEW|INDEX` heads and asserts the files containing one are exactly `schema.py` plus a visible `DDL_SCRATCH_FILES` exemption set, which a test file earns only by confining its DDL to throwaway probe objects that are never layout names (`tests/test_workspace_types.py` probes column types on tables it creates in-memory; `tests/test_workspace_lifecycle.py` plants foreign objects in throwaway files to pin that rw `open()` refuses a foreign database; equality rather than containment keeps a stale exemption from lingering); a second keys on the name each head *creates* — bare or schema-qualified, through the `IF NOT EXISTS`/`OR REPLACE` spellings — and forbids every file but `schema.py` from creating a layout name, derived from `EXPECTED_TABLES` plus the `meta` schema so a table added to `_DDL` is protected without a second list, which is what makes the exemption safe: a scratch file may create `t`, never `pkts`, and merely *querying* `pkts` is fine anywhere; the third counts the heads inside `schema.py` against those in `iter_ddl()` so no helper can build DDL inline. `naming.column_name` is the frozen abbrev → column policy, shared with #26 by import rather than restatement so the schema and type layers cannot disagree about column names: it keeps the **full** abbrev — no parent stripping, unlike `codegen/mangle.py`, where `tcp.port` safely shortens to `port` on `TCP`, because columns share one flat namespace inside `pkts` and `tcp.port`/`udp.port` must stay distinct — lowercases it because DuckDB compares identifiers case-insensitively (so `ip.Src` and `ip.src` *are* one column, and lowercasing surfaces that as a collision instead of a silent overwrite), maps non-ASCII-alphanumerics to `_`, and prefixes a leading digit with `f_`. Like the attribute policy it is **not injective** (`tcp.port` and `tcp_port` both yield `tcp_port`), so running `find_collisions` and refusing is mandatory before materializing a field set, not advisory; `ColumnNameCollisionError` is the exported type for that refusal (nothing raises it yet — materialization is #31's), and storage backs the rule up with a `UNIQUE` on `meta.fields.column_name` so two abbrevs can never claim one column even if a caller skips the check. `naming.SKELETON_COLUMNS` names the two columns `pkts` is born with, reserved because they are already materialized: `find_collisions` cannot flag them (they collide with nothing), so `add_field_column` refuses them by name with "already the row key" rather than the generic duplicate-column message. Column types come from the caller and `types.py` is where callers get one; `schema.py` stays type-agnostic and never derives a column type from an ftype itself. A SQL type cannot be bound as a parameter, so `add_field_column` validates `sql_type` against a conservative pattern and quotes the column name; both its duplicate check and its `ALTER` are pinned to `main.pkts` / `current_database()`, because `duckdb_columns()` spans attached databases and would otherwise see a foreign table's column as a duplicate. Timestamps are UTC and never `TIMESTAMPTZ`, which DuckDB renders through the session time zone so one file would print different timestamps on different machines: DuckDB `TIMESTAMP` is timezone-naive, so aware datetimes are converted to naive UTC on write and re-tagged UTC on read, and a naive datetime handed in is taken to be UTC already. The `to_db_timestamp`/`from_db_timestamp` pair implementing that lives in `types.py` since #26 (it is `FT_ABSOLUTE_TIME`'s codec pair), and `schema.py` imports it for its catalog columns so the two layers cannot drift apart on the convention. `CacheKeyRecord.fields`/`.argv` are stored in native `VARCHAR[]` columns and read back as tuples, so #32's subset rule is a `list_has_all` predicate in SQL rather than a fetch-everything-and-decode scan, and the workspace file stays directly queryable. duckdb is the optional `remora[workspace]` extra (and part of `remora[all]`): every module here is import-pure — `DuckDBPyConnection` is annotated under `TYPE_CHECKING`, so importing the package never imports duckdb, and the one runtime import lives inside `workspace.py`'s connect helper, reached only when a connection is actually opened — and connections are caller-supplied everywhere outside `workspace.py`, because connection and lock ownership belongs to the `Workspace` class (#28). `SCHEMA_VERSION` (1) is written into `meta.info` at creation; a missing `meta.info` or missing version row means "not a remora workspace" (probed with `database_name = current_database()`, like the duplicate-column check, so an attached workspace cannot vouch for a blank current database), and `check_compatible` accepts only the exact version, naming both in either direction: there is no migration path, and an older file has to be refused loudly because `create_schema` is `IF NOT EXISTS`-only and would no-op on the stale tables. `create_schema` does not imply `check_compatible`; #28's opener must call both. `workspace.py` (#28) is that owner and the only module in the package that opens a connection: `Workspace(path, mode="ro")` is a context manager whose default is read-only because DuckDB's single-writer lock means one long-lived read-write connection blocks every other process's reads — ro mode holds one long-lived read-only connection (a shared lock, so concurrent readers are unaffected) while `rw` mode holds **no** connection between operations, `write()` opening a short-lived read-write connection around exactly one transaction (commit on clean exit, rollback on exception, close either way) so the exclusive lock is released promptly, and `read()` in rw mode opening read-write rather than read-only because DuckDB refuses two live same-process connections to one file with different configurations and a read may nest inside `write()`. That last concession has two consequences a caller has to know: an rw-mode read holds the exclusive lock for its whole duration, so a long read under `mode="rw"` locks other processes out exactly like a write does and a read-mostly caller wants `mode="ro"`; and a read nested inside `write()` runs on its own separate connection, so it does not see the enclosing transaction's uncommitted rows. Opening always runs `check_compatible`, and rw mode runs `create_schema` first only when the database holds no user objects at all — tables, views, sequences, macros, user types and schemas alike, each probed via `current_database()` like every other catalog probe, because a foreign database is not necessarily betrayed by a table and counting only `duckdb_tables()` let a view-only file be adopted and half-upgraded — so a foreign or stale file is refused instead; ro mode on a missing file is an error naming `mode="rw"`, and the write APIs in ro mode raise `WorkspaceModeError` saying the same thing. A checkpoint truncates only *trailing* free blocks, so emptying a table largely shrinks the file by itself while scattered deletes leave interior free blocks the file keeps forever — which is what `compact()` (rw only) exists for: it rewrites every schema, table and row into a sibling `<name>.compacting` temp file with `COPY FROM DATABASE` and swaps it in atomically with `os.replace`, so an interruption at any point leaves the original intact and at worst a stale temp file — plus the `.wal` sidecar a hard kill mid-copy can leave beside it, unlinked wherever the temp itself is — that the next compact removes. The rewrite runs on a read-write connection to the *source* (only the temp is attached, as `compact_dst`) and the `os.replace` happens while that connection is still open, so the source's exclusive lock is held across both the copy and the swap: another process's writer either commits before compaction begins — and is therefore copied — or fails fast on the lock until the swap completes, and no commit can land in a close→replace gap and be silently discarded, which is exactly what an in-memory connection with a read-only attach used to allow. The price is that every other process, readers included, is locked out from the moment the lock is taken *through the atomic rename* — the rename, not the return, is the cross-process linearization point, because it installs a new inode the old file's lock does not cover, so another process may connect the instant it lands, safely: such a write goes into the compacted file and survives (a pinned test commits one there), where same-process writers stay excluded until the source connection closes because an admit would join the pre-swap instance — and conversely compaction needs sole access, failing fast on DuckDB's lock error if any other process (a read-only reader included) is already connected, with nothing modified — and that a same-process `write()` or rw-mode `read()` shares this instance and would *not* hit the lock, which the file lock therefore cannot arbitrate: a module-level registry keyed by the file's **identity** — `(st_dev, st_ino)` from an `os.stat`, recomputed per operation and never cached because `compact()` swaps the inode, falling back to the resolved pathname only for a file that cannot be stat'ed — does it instead (plain counters and a flag, never a connection — the no-module-level-*connection* rule is about connections). Identity rather than pathname is the fix for a reviewer-reproduced hole: a `realpath` string preserves spelling, so on a case-insensitive filesystem `ws.duckdb` and `WS.DUCKDB` keyed differently and a second `Workspace` could commit *during* the swap and have it discarded — and a hard link did the same on every platform. Keying on the inode makes every spelling, symlink and hard link of one file coordinate as one — and because an identity key is exactly what `compact()` swaps, `compact()` holds its flag under **both** the old and the new identity (claiming the temp's the moment the temp is final, releasing both only *after* the source connection is closed) while writers re-stat the file once their slot is held and retry if the identity moved: without the first half a writer that stats the path after the `os.replace` finds no entry, is admitted, joins the pre-swap DuckDB instance (its cache keys on the *path*, which compact's source connection still holds) and commits into the file that was just thrown away — a second reviewer-reproduced silent loss — and without the second half a writer that stalls across an entire compact holds a slot under a dead key and no longer blocks the next one. `compact()`'s own claim gets the same treatment: another *process's* compact can swap the inode at any instant this one does not hold the file's exclusive lock, so the source connection is opened inside the claim loop and the identity re-checked while both the flag and the lock are held — no swap can happen under the lock, so a match proves the flag covers the live file for as long as the connection stays open, and a mismatch closes the connection, drops the flag and retries against the new file (a third reviewer-reproduced loss: a child-process compact completing in the claim-to-connect gap left the flag on a dead inode, and a same-process writer keyed on the live one was admitted mid-swap). Coordination follows file identity, so writes are locked out through every alias for a compact's whole duration, swap included. The registry keys being tuples is why `_acquire_write_slot`/`_begin_compact` take the `Path` alongside the key: the error messages name the path. The residual is inherent to atomic swap rather than a coordination gap: a hardlinked alias still points at the *old* inode once a compact through another name completes, so the two names diverge after a successful compact — never during one. That coordination makes `write()`/rw-`read()` and `compact()` mutually exclusive across every `Workspace` object and thread in the process, so `compact()` raises `WorkspaceError` on an in-flight body of *any* instance rather than swapping the file out from under it, a second concurrent `compact()` is rejected the same way, and for compaction's duration writers and rw-mode readers fail fast with `WorkspaceError` exactly as a second process fails on the file lock — the case a reviewer reproduced as silent data loss when the counter was per-instance. Cleanup of a stale `.compacting` temp and its `.wal` happens only *after* the exclusive lock is acquired, so a lock-conflicted `compact()` modifies nothing at all, another process's in-flight temp included — and that failed connect is wrapped too, so losing the lock (a second process, or an ro-mode `Workspace` on this file in *this* process, whose long-lived read-only connection DuckDB will not let a read-write one join) reads as a `WorkspaceError` about needing sole access rather than a raw duckdb exception. `compact()` also works on the path's `realpath`, not the path as given: a workspace addressed through a symlink is compacted at its resolved target, so the temp lands beside the real file and the swap replaces the real file, leaving the alias a symlink instead of turning it into an independent regular file (a *hard* link cannot be preserved that way — the replaced name gets the new inode while the other name keeps the old one — which is the documented residual above). The temp is a brand-new file, so it is born with umask defaults and would silently widen a `0o640` workspace to `0o644`; `compact()` therefore copies the source's mode bits onto the temp between the `DETACH` and the `os.replace`. Ownership and other metadata follow the fresh file, since `chown` needs privileges compact does not assume. The swap-under-lock design is **POSIX-only today**: Windows refuses a rename over a file the process holds open, so there `compact()` raises `WorkspaceError` naming the limitation (#85) instead of surfacing a bare `PermissionError`, and the original is left intact — and that wrapping is deliberately narrow, catching only `PermissionError` so any other `OSError` from the rename propagates as itself. duckdb is imported lazily inside the connect helper, which is what makes a module-level connection impossible (`tests/test_workspace_import_purity.py` deliberately carries no `importorskip`, so its fresh-interpreter check — no duckdb in `sys.modules`, and on Linux no file handle left open — and its missing-duckdb `ImportError` check run precisely where duckdb is absent), and a missing duckdb raises `ImportError` naming `pip install 'remora[workspace]'`. `types.py` (#26) is `values.py`'s other half: `values.py` owns raw tshark text → Python value, `types.py` owns that Python value ↔ what DuckDB stores, and nothing else in the tree maps an ftype to a SQL type. `COLUMN_TYPES` covers exactly `values.FTYPE_TABLE`'s ftype universe (a test asserts the two key sets are equal, so an ftype added there cannot silently fall out) and is **frozen** — a workspace written by one remora is read by the next, so changing a column type is a storage-format change, not a tweak. Addresses are stored as their integer form (`FT_IPv4` → `UINTEGER`, `FT_IPv6` → `UHUGEINT`) so subnet matching degrades to a `BETWEEN` over an ordered column that DuckDB's zone maps can skip row groups on (epic #43), where a text column would force a per-row parse; integer ftypes keep their exact width for the same reason, since a blanket `BIGINT` would cost 8x the bytes on `FT_UINT8` and widen every zone map's range. `FT_FLOAT` is `DOUBLE`, not `FLOAT`, because `values.py` parses it with `float()` to a Python double and `FLOAT` would round every value on the way in, making the round trip lossy; `FT_RELATIVE_TIME` is `INTERVAL`, which round-trips `timedelta` natively and dodges the usual month-component ambiguity because a `timedelta` never carries months (`avg`/`min`/`max`/`median` take an `INTERVAL` directly, but `sum` and `quantile_cont` do not, so #32 must route a total or a p95 through `epoch(v)`); `FT_ETHER` is `BLOB` because `values.py` yields 6 raw bytes rather than text; an unknown ftype falls back to `VARCHAR` with identity codecs, mirroring `values.get_info`'s fallback to `str`. There is no pyarrow dependency (nor a duckdb one — SQL types are plain strings and encoded values plain Python), but the module's table documents the Arrow equivalent per ftype for #31, along with the export hazard #31 must respect: DuckDB exports `UHUGEINT` through Arrow as `decimal128(38, 0)` read as **signed**, so every `FT_IPv6` address with the high bit set — all of `fe80::/10` link-local and `ff00::/8` multicast, i.e. essentially every real capture, not a top-of-the-range corner case — comes back two's-complement negative; the DuckDB-native path is exact (tests pin the addresses either side of 2^127), which is what keeps `UHUGEINT` the right column type — but that exactness is not free, and `FT_IPv6` is the one ftype whose encoder emits a **decimal string** rather than the `int` its column type suggests: DuckDB unifies a Python list's *inferred* element types before casting them to the column type, so an element below 2^63 (`::`) alongside one above 2^127 (`ff02::1:2`) unifies to signed `HUGEINT` and the bind fails outright, and an explicit `?::UHUGEINT[]` cast does not help because the unification happens first. A DAD Neighbour Solicitation puts exactly that pair into one `ipv6.addr` list, so #31 would hit it on ordinary traffic; `VARCHAR` casts to `UHUGEINT` in scalar and list position alike, so the column type, the read-back `int`, and `list_contains(v, <int>)` are all unchanged. No other ftype needs it — no other column type reaches 2^127 — so do not broaden it. `column_spec(abbrev, ftype, multi)` is the single per-field call #31 needs, pairing `naming.column_name` with the SQL type and codecs: a multi-value field's column is the scalar type's `LIST` (`T[]`), an absent scalar encodes to `None` and an absent multi to `[]` — never `NULL` in a list column, because `list_contains(NULL, x)` is `NULL` while `list_contains([], x)` is `false`, and `false` is what the predicate backend means by "an absent field never matches" (a `NULL` read back from a multi column still decodes to `()`, since a column added later back-fills `NULL` on older rows) — and a field declared scalar that occurs more than once in a packet raises `ValueError` rather than keeping the first and silently dropping data. `cachekey.py` (#27) computes what #32 later compares: `fingerprint_pcap` identifies a capture by `st_size`, `st_mtime_ns` and a sha256 over its first and last 64 KiB — never a whole-file digest, because materializing a multi-gigabyte capture must not first read it twice, and never the float `st_mtime`, because integer nanoseconds are exact and platform-stable. The sample digest deliberately excludes size and mtime so the three components stay separable in the rendered `fp1:size=…:mtime=…:probe=…` string, and it buys its cheapness with a real blind spot: an in-place edit to the middle of a large file that changes neither length nor mtime fingerprints identically, which a named test pins so it stays a known trade-off rather than becoming an incident. `make_cache_key` digests the rendered fingerprint, the projection field set, the dfilter, the tshark version and the **full effective argv** — verbatim and order-sensitive, because a different `-X lua_script:`, `-d` or `-o` dissects identical bytes into different fields, which is exactly the omission that makes a cache silently wrong. Components are length-prefixed before hashing so no argument boundary is ambiguous (`-rcap.pcap` cannot digest as `-r cap.pcap`), the field set is sorted and deduplicated so projection order never flips the key and #32's `list_has_all` subset test sees a canonical set, `None` and `""` dfilters digest differently, and the key carries a `ck1:` scheme prefix so a future change to the scheme invalidates stored keys visibly instead of sharing one namespace with a second scheme. `pcap_path` is stored for diagnostics but not hashed — argv already carries the path tshark was given. The digest is sha256 throughout and never `hash()`, so keys are stable across processes; a pinned golden digest and a subprocess run under a randomized `PYTHONHASHSEED` both guard that. The function returns #25's `CacheKeyRecord` rather than a bare digest precisely so the components that were hashed and the components that get written cannot drift apart. That pairing is also why the two layers hold different contracts: `_to_bytes` encodes with `surrogateescape` so hashing is total and can never raise, while `make_cache_key` separately refuses any component DuckDB `VARCHAR` cannot hold — a lone surrogate, which is what `os.fsdecode` yields for a non-UTF-8 POSIX path or argv element. Ordinary non-ASCII stores and round-trips fine; only the unstorable case is refused, with a `ValueError` naming the component, raised before the capture is read. Storing it losslessly instead would need a reversible text encoding of arbitrary bytes inside `VARCHAR`, which is a storage-format change and a `SCHEMA_VERSION` bump, so the boundary is drawn here rather than in #25.
  `annotations.py` (#30) is the mutable half of the workspace — the reason it is DuckDB native storage and not immutable Parquet — and it uses #25's `main.annotations` columns exactly as they stand (`annotation_id`, `scope`, `target_id`, `key`, `value`, `created_at`), so `SCHEMA_VERSION` stays 1. Like every module here but `workspace.py` it takes a caller-supplied connection and does no I/O of its own; the user-facing entry points are five thin `Workspace` methods (`add_annotation`, `remove_annotation`, `remove_annotations`, `delete_orphan_annotations`, `list_annotations`) that are each exactly one `write()` transaction — or one `read()` for listing, which is why listing works in ro mode while the four write methods get `WorkspaceModeError` from `write()` itself, and why no connection is held between calls. A packet annotation is keyed by frame number alone because `pkts` has no capture column: `frame_number` is its row key, so one workspace holds one capture and the *file* is the capture identity, with `meta.cache_keys` (`pcap_path`/`pcap_fingerprint`) recording which capture that is; a multi-capture workspace would need a capture column in `iter_ddl()` and a `SCHEMA_VERSION` bump. `annotation_id` comes from a monotonic high-water mark stored in `meta.info` under `next_annotation_id` rather than from a sequence or from `max(annotation_id) + 1`: a sequence is unavailable because `create_schema` is `IF NOT EXISTS`-only and runs only on an empty database, so an existing workspace could never acquire one added later, while `max+1` was both non-unique and non-monotonic — 20 same-process threads each in their own `write()` transaction all committed id 1 (DuckDB's file lock serializes writers across processes but not within one), and deleting the highest-numbered annotation freed its id for the next add to reuse, so a stale id came to name — and `remove_annotation` to delete — a different finding. `meta.info` is the generic key/value catalog table every v1 workspace already has, so the allocator needs no layout change and no `SCHEMA_VERSION` bump; the mark is read and advanced inside the caller's transaction alongside the annotation row, so the id a commit used is never handed out again (a deleted id is gone for good and a stale one now matches nothing, returning `False`) and two racing same-process transactions both write that one row and DuckDB refuses the loser loudly — `duckdb.TransactionException` when both update an existing mark, `duckdb.ConstraintException` on `meta.info`'s primary key when both seed a missing one — rolling its whole add back instead of silently sharing an id. A workspace written before the key existed has no mark: the first add seeds it lazily from `max(annotation_id) + 1`. The orphan policy is **kept-but-flagged**: annotations are analyst findings, so a re-materialization under a narrower filter never deletes them — `list_annotations` derives `AnnotationRecord.orphaned` at read time (an EXISTS against `pkts`/`streams` rather than a LEFT JOIN, because `pkts` has no `PRIMARY KEY` and a join would fan one annotation out on a repeated frame number), a wider filter un-orphans them again, and `delete_orphan_annotations` is the one explicit call that removes them. `remove_annotations` refuses a call with no filters, because wiping every finding is too destructive to be what zero arguments means.

Cross-cutting invariants:

- `tests/test_proto_seed.py` pairing tests are the frozen-format contract, running against all generated core modules (reshaped in #19 when the generated tree replaced the hand-written seeds) — from here on, keep them passing unmodified.
- Attribute names come from the frozen mangle policy (`src/remora/codegen/mangle.py`) at generation time; `_table_` stores the full tshark name precisely so nothing at runtime may re-derive tshark names from attribute names or vice versa.
- Absence is `()` from `get_raw`, `None` from scalar instance access, `()` from multi instance access — never an exception (except `FieldNotProjectedError` for fields outside a `-T fields` projection).
- Underscore-prefixed attributes on protocol classes are reserved; ruff RUF012 requires the `ClassVar[FieldTable]` annotation on tables.
- `tests/conftest.py` provides `FakePacket`, the standard `RawPacket` test double.
